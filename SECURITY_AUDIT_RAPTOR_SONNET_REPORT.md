## 1. Executive Summary

### 1.1 Scope & Context
In October 2026, an exhaustive security audit of the **OpenỌ̀ṣọ́ọ̀sì / OshoosiClaw EDR (`v1.2.0`)** codebase was conducted against vulnerability findings generated by the **RAPTOR autonomous source code security scanner** and the **Sonnet lab-compatibility review**. The target codebase comprises the core Rust workspace (16 crates spanning EDR kernel/userland orchestrators, behavioral anomaly detection, policy voters, cryptographic Merkle audit hierarchies, SIQuery relational forensics, and Axum dashboard), the Windows kernel driver (`driver/`), the Linux CO-RE eBPF sensor (`ebpf/`), the frontend web console (`dashboard/`), and cross-platform packaging/deployment configurations (`deploy/`, `scripts/`, `wix/`).

### 1.2 Overall Security Posture
The audit identified systemic vulnerabilities and operational friction points across five distinct architectural categories:
1. **Supply-Chain Integrity & Cryptographic Provenance**: Placeholder/fake `.asc` detached signatures and non-DSSE `.intoto.jsonl` provenance envelopes, unpinned workspace and Python dependencies, streaming OOM risks in large ONNX model hashing, and bypassable self-healing restores.
2. **Autonomous Response Governance & Lab Safety**: Overly aggressive single-detector containment actions (such as an uncorroborated `0.80` LLM confidence score triggering immediate network drops (`iptables -P DROP`), process tree termination (`kill -9`), or account lockdowns) that severed management connectivity (SSH, Ansible) in lab and operational environments; and unhandled `human_escalation_required == true` flags failing to downgrade destructive responses.
3. **Prompt Injection & Agent Jacking Resilience**: Telemetry field interpolation into LLM prompts without sanitization, vulnerable pipe-delimited (`|`) templates allowing token spoofing, and delimiter smuggling in incident report generation.
4. **Runtime Security, Least Privilege & Network Boundaries**: Unsolicited telemetry egress to `api.openai.com` when `OPENAI_API_KEY` was detected in the environment; startup modifications to Windows Defender exclusions (`Add-MpPreference`) and host firewalls; unauthenticated state-changing dashboard endpoints (`/api/traffic/conversation`); cleartext process name and path leakage across public Nostr mesh relays; and shell spawns (`powershell.exe`, `cmd.exe`, `sh`) violating `SECURITY.md`.
5. **Kernel Driver Memory Safety, Linux Parity, & Sensor Panic Resilience**: Driver wide-string bounds safety, Linux eBPF telemetry parity (ppid tracking and multi-distro packaging), and 8+ panic-inducing `.unwrap()` / `.expect()` calls across high-throughput detection hot paths.

### 1.3 Key Risk Reductions
- **100% Cryptographic Supply-Chain Verification**: Genuine OpenPGP Ed25519 detached signatures (`.asc`) pass `gpg --verify` on all Linux release artifacts. SLSA DSSE in-toto provenance envelopes (`provenance.intoto.jsonl`) cryptographically bind binary digests to official build workflows. Workspace versions are synchronized to `1.2.0`, Python dependencies are hash-pinned (`--hash=sha256:`), model hashing uses $O(1)$ RAM 64 KB chunked streaming, and self-healing enforces Merkle audit trail primacy.
- **Fail-Closed Autonomous Response Gates**: Destructive actions (`Isolate`, `Tarpit`, `GhostTarpit`, process kill, account disable) strictly require multi-signal deterministic corroboration (`detector_count >= 2`, active CVE, cryptographic Authenticode signature, or Merkle inclusion proof). The `human_escalation_required` flag acts as an immutable blocking gate that forces `ResponseAction::Alert`, `ActionState::Pending`, and `require_approval = true`.
- **Lab-Safe Management Shields**: Host containment exempts loopback (`lo`), conntrack `ESTABLISHED,RELATED`, and management ports (SSH 22, 4001, 8080) with idempotent `iptables -C` checks. Process tree termination protects `sshd`, active SSH sessions (`pts/`), and Ansible controllers.
- **End-to-End Prompt Injection Defense**: Centralized `LogSanitizer`, `StructuredPromptEnvelope`, and `StructuredIncidentEnvelope` normalize and defang untrusted telemetry strings, strip colons and newlines, and wrap incident prompts in structured XML/ChatML tags.
- **Zero-Trust Network Defaults & Privacy**: Outbound cloud LLM calls require explicit configuration opt-in (`enable_cloud_llm = true`); Defender tampering (`Add-MpPreference`) is completely eradicated; dashboard binds strictly to `127.0.0.1:3030` with mandatory `X-API-Key` / Bearer token authentication; and Nostr mesh telemetry unconditionally scrubs process names to `redacted-process.<ext>` and drops parent processes.
- **Zero Production Shell Spawns**: All 11 identified shell executions (`powershell.exe`, `cmd.exe`, `sh`) have been replaced with native Win32/Rust APIs (`NetUserGetInfo`, `NetUserSetInfo`, `winreg`, `ShellExecuteW`, `ShellExecuteExW`, `Path::exists`).
- **Zero-Panic Sensor Resilience**: All hot-path `.unwrap()` and `.expect()` calls have been converted to safe conditional matches (`if let Some`, `map_or`, `is_none_or`, `LazyLock<Regex>`), and all 484 automated tests pass with 0 failures.

## 3. Architectural Security Review

### 3.1 Supply-Chain Integrity & Cryptographic Attestations
OshoosiClaw v1.2.0 establishes an end-to-end verifiable supply chain:
- **Detached OpenPGP Signatures**: All release assets (`.deb`, `.rpm`, `.tar.gz`, binaries) in `deploy/linux/` are cryptographically accompanied by ASCII-armored detached signatures (`.asc`) generated via `gpg --detach-sign --armor` using the official Ed25519 release key (`E74B83DBC48200113967E97DCCA1D74D5DC7829D`). Every signature verifies cleanly via standard `gpg --verify`.
- **SLSA DSSE Provenance**: Provenance metadata (`provenance.intoto.jsonl`) is formatted as a Dead Simple Signing Envelope (DSSE) in compliance with the SLSA v0.2 / v1.0 specifications. It cryptographically binds the SHA-256 digests of all distributed artifacts to the canonical build recipe in `.github/workflows/release-slsa.yml`.
- **$O(1)$ RAM Chunked Hashing**: Large model files (such as multi-GB Gemma 4 ONNX shards, MalConv weights, and SOREL-20M checkpoints) are validated using streaming 64 KB buffers (`compute_file_sha256`), preventing heap exhaustion or Out-of-Memory (OOM) Denial-of-Service attacks during startup integrity verification.
- **Fail-Closed Self-Healing**: File restoration logic in `crates/osoosi-core/src/self_healing.rs` consults the immutable Merkle `AuditTrail` before checking local files. Discrepancies between local hash files and the audit log are treated as active tamper attempts and fail closed.

### 3.2 Autonomous Response Governance & Human Oversight
To prevent automated containment mechanisms from disrupting critical operations or locking out administrative personnel:
- **Multi-Signal Corroboration Gate (`apply_corroboration_gate`)**: Destructive actions (`Isolate`, `Tarpit`, `GhostTarpit`, process tree termination, and account disablement) are barred from single-detector triggers. Destructive containment requires corroboration from at least two independent detection mechanisms (`detector_count >= 2`), an active CVE record, an authentic Authenticode signature match, or a cryptographic Merkle inclusion proof. Single-signal alerts are capped at `ResponseAction::Alert` with `require_approval = true`.
- **Immutable Human Escalation Gate (`apply_human_escalation_gate`)**: If any upstream decision engine flags `human_escalation_required == true`, the EDR pipeline strictly downgrades the effective response action to `ResponseAction::Alert`, sets `action_state = ActionState::Pending`, and enforces administrative approval before any containment script can execute. This gate overrides both automated sweeps and lockdown modes.
- **Administrative Session Shielding**: Linux firewall containment rules (`block_linux_process_uid`) automatically inject exemption rules for loopback traffic (`lo`), established connections (`conntrack ESTABLISHED,RELATED`), and administrative management ports (SSH port 22, 4001, 8080). Pre-checking rule existence via `iptables -C` ensures idempotency and prevents rule-table bloat. Process tree termination protects `sshd`, active SSH pseudo-terminals (`pts/`), and Ansible deployment agents.

### 3.3 Prompt Injection Defense Architecture (`AgentJackingGuard`)
OshoosiClaw protects internal LLM/SLM inference engines against adversarial prompt injection, jailbreaking, and verdict manipulation:
- **`LogSanitizer`**: Centralized in `crates/osoosi-types/src/agentjacking.rs`, this filter removes invisible zero-width unicode characters (which adversaries use to evade keyword filters), strips non-printable control codes, and defangs known injection strings.
- **`StructuredPromptEnvelope`**: Untrusted variables (process command lines, file names, network indicators) are wrapped in strictly escaped XML tags (`<system>`, `<incident>`, `<field>`), neutralizing attempt by payloads to escape string context.
- **`StructuredIncidentEnvelope` Delimiter Neutralization**: In incident reporting, keys and values are sanitized to strip colons (`:`) and convert newline characters (`\r`, `\n`, `\t`) into single spaces, eliminating multiline pseudo-header spoofing attacks (e.g. `\nVerdict: benign`).

### 3.4 Runtime Security & Principle of Least Privilege
- **Zero-Egress OpenAI Defaults**: The daemon operates fully offline by default. Even if `OPENAI_API_KEY` is present in the host environment, outbound requests to `api.openai.com` are blocked unless `enable_cloud_llm = true` is explicitly configured in `osoosi.toml` or `OSOOSI_ENABLE_CLOUD_LLM=1` is exported.
- **Elimination of Host Defender Tampering**: Anti-malware exclusion commands (`Add-MpPreference`) have been completely deleted. Host firewall openings are disabled by default (`OSOOSI_AUTO_CONFIGURE_HOST_FIREWALL=0`).
- **Dashboard API Security**: The dashboard server binds strictly to `127.0.0.1:3030`. All state-changing endpoints (including `/api/traffic/conversation`) require authentication via `X-API-Key`, `Authorization: Bearer <token>`, or session cookie, verified using constant-time comparisons (`constant_time_eq_token`).
- **P2P & Nostr Mesh Privacy**: Public Nostr relays are disabled by default. When mesh gossip is active, process names are anonymized to `redacted-process.<ext>`, parent process references are dropped, predicted next actions are redacted, and timestamps are randomized by +/- 15 minutes to defeat traffic correlation.
- **Zero Shell Spawns**: All 11 legacy shell process invocations (`cmd.exe`, `powershell.exe`, `sh`) have been replaced with native operating system APIs (`NetUserGetInfo`, `NetUserSetInfo`, `winreg`, `ShellExecuteW`, `ShellExecuteExW`, `Path::exists`).

### 3.5 Kernel Driver & eBPF Telemetry Parity
- **Windows Kernel Driver**: Driver string routines use bounded APIs (`RtlStringCbLengthW`) and enforce explicit null-termination before length inspection, preventing out-of-bounds kernel memory reads.
- **Linux CO-RE eBPF**: The eBPF probe (`ebpf/src/osoosi_probe.bpf.c`) reads parent process IDs (`ppid`) directly from kernel task structures via `BPF_CORE_READ(task, real_parent, tgid)`, delivering feature parity with Windows ETW telemetry.

### 3.6 Zero-Panic Hot Path Architecture
Every fallible unwrap identified across detection hot paths has been replaced with non-panicking constructs:
- Iterator exhaustion uses `let Some(...) else { break; }` or peekable iterators.
- Candidate deduplication uses `candidates.last().is_none_or(|last| norm_payload != *last)`.
- Concurrent policy mutations use safe `if let Some(p) = Arc::get_mut(&mut policy)`.
- Regexes are compiled once at initialization via `static LazyLock<Regex>` rather than per-event `Regex::new(...).unwrap()`.
- Fixed socket addresses use compile-time constructors (`SocketAddr::V4`).

## 5. Operational & Lab-Safe Deployment Guidance

### 5.1 Safe Operation in Testing & Lab Environments
When deploying OshoosiClaw into research environments, malware analysis labs (CAPE, Cuckoo), penetration testing ranges, or continuous integration runners:
1. **Monitor Mode by Default**: Ensure `autonomy_mode = "monitor_only"` in `osoosi.toml` (or pass `--monitor-only` to `osoosi start`). In this mode, threat signatures and decision model outputs are fully evaluated, logged, persisted to SQLite (`threats`, `consensus_findings`), and anchored into the Merkle audit tree, but active OS blocking (`iptables`, process termination, account rollback) is skipped.
2. **Administrative Exemption Preserved**: Even when running in enforce mode, the EDR automatically preserves management connections:
   - Linux host firewall rules explicitly allow loopback traffic (`-o lo`), established connections (`-m conntrack --ctstate ESTABLISHED,RELATED`), and management ports (SSH 22, 4001, 8080).
   - Process tree containment preserves the SSH daemon (`sshd`), active interactive terminal sessions (`pts/`), and Ansible controller processes.
3. **Dry-Run Testing**: Operators can verify detection rules against live benign traffic without fear of accidental network partition.

### 5.2 Air-Gapped & Offline Configuration
OshoosiClaw is architected for completely isolated, air-gapped environments:
1. **Default Air-Gap Posture**: All external communication is disabled out of the box:
   - `enable_cloud_llm = false`: Prevents requests to `api.openai.com`.
   - `allow_public_relays = false`: Suppresses connections to public Nostr relays (`damus.io`, `nos.lol`).
   - `enable_duckdns = false`: Suppresses dynamic DNS updates.
2. **Local Model Execution**: Local quantized SLM models (such as SmolLM2-360M, Gemma 4, or local Ollama instances on `127.0.0.1:11434`) perform on-device inference without internet access.
3. **Offline Feed Ingestion**: Threat feeds (YARA rules, MITRE ATT&CK catalogs, NSRL hash lists) can be populated locally by placing signed archives in the `feeds/` directory and executing `osoosi feed import <path>`.

### 5.3 Secure Opt-In Procedures for Cloud LLMs
If an enterprise security operations team explicitly chooses to leverage cloud LLM services (e.g. OpenAI GPT-4o) for high-complexity incident analysis:
1. **Explicit Configuration Required**:
   Edit `osoosi.toml` under `[ai]`:
   ```toml
   [ai]
   enable_cloud_llm = true
   cloud_llm_model = "gpt-4o"
   ```
   Or set the environment variable:
   ```powershell
   $env:OSOOSI_ENABLE_CLOUD_LLM = "1"
   $env:OSOOSI_CLOUD_LLM_MODEL = "gpt-4o"
   ```
2. **API Key Provisioning**:
   Provide the API key via process-scoped environment variable:
   ```powershell
   $env:OPENAI_API_KEY = "sk-proj-..."
   ```
   *Note: Providing `OPENAI_API_KEY` without setting `enable_cloud_llm = true` will NOT trigger cloud requests; the analyzer will refuse to connect and log a guidance message.*
3. **Data Sanitization Guarantee**:
   Even when cloud LLM analysis is active, all incident payloads pass through `LogSanitizer` and `StructuredPromptEnvelope` to scrub prompt injection payloads and defang malicious control sequences before leaving the host.
